Recently, I've been messing about with Git server stuff for some experimental work for [GitButler](https://gitbutler.com). In doing that, one of the things that I've been digging into is the [bundle-uri](https://blog.gitbutler.com/going-down-the-rabbit-hole-of-gits-new-bundle-uri) and [packfile-uri](https://git-scm.com/docs/packfile-uri) capabilities.

However, it made me realize that I'm not as familiar with how Git's HTTP service works these days as I thought I was.

## Smart HTTP, First Edition

When I published the first version of the [Pro Git book](https://git-scm.com/book/en/v2) in August of 2009, Git barely had HTTP support at all. What it had then is now referred to as the "dumb" protocol, just serving static files directly over HTTP.

In December of 2009, Git 1.6.6 landed with the first "smart" protocol - a CGI script you could load into Apache or whatever to handle ref advertisement and object negotiation via new `git-upload-pack` and `git-receive-pack` binaries.

That smart-HTTP support landed as part of a sprawling 28-patch series from Shawn O. Pearce on the Git mailing list — the origin of `git-http-backend` and the smart client and server we still use:

Since this landed after Pro Git was published, one of the bigger updates in the second edition of the book was to make HTTP a first class protocol to use. I also wrote a blog post [here](/2010/03/04/smart-http/) outlining the changes in the meantime.

## HTTP Protocol V2

I published the second edition of Pro Git in November of 2014 updated with these changes, and a few years later the HTTP transport got smarter _again_ with the _v2_ protocol.

Since I wasn't as heavily into Git stuff for a bit, I sort of missed what this meant and why it was done, so I've recently dug into it. If you're curious how Git's modern HTTP protocol works, this is the blog post for you.

### Why a New Protocol?

The first version of the smart protocol would basically do a dump of every reference when you first connected, so the client could determine what objects it had or needed and continue to the negotiation or object push.

That's fine for most projects, but when your repository has hundreds of thousands of refs, it becomes a lot of data to send over the wire every time you want to do anything at all. So one of the first things the new protocol could do was filter the refs advertised with the `ls-refs` command.

Another problem was capabilities advertisement. The first version sort of shoehorned them in to the first reference line, hidden behind a NUL byte, which means a server could never advertise more than the size of a pkt-line.

Finally, instead of multiple service names, in v2, multiple commands can be supported by a single service. This means that instead of adding new commands by adding new http endpoints, the `git-upload-pack` service can now be asked to do lots of different things other than producing packfiles (like listing filtered references, for example).

To lay the foundation to address these issues, Brandon Williams of Google introduced `git-serve` in March 2018, along with the first two capabilities, `ls-refs` and `fetch`. It finally became the default protocol for the client in Git 2.29, released in October 2020.

## Anatomy of a Git HTTP conversation

OK, so what did an HTTP conversation look like with the first protocol and what does it look like with v2? Let's walk through a clone of a small repository to see the difference.

### The First Protocol

Originally, the "Smart" HTTP conversation went something like this.

For a clone, the client would make two HTTP round trips. One to figure out what the reference tips (branches) are. The second to tell the server what it wanted so the server could generate a packfile of just the data needed.

Let's look at each HTTP request in a bit of detail. The first roundtrip is a GET request that asks for references and server capabilities.

### The v2 Protocol

The newer protocol starts with a capability advertisement - what can the server _do_? Then the client can run one or more of those commands.

  </p>

OK, so now the client knows what the server can do, including what object format the repository is in (`sha1` or `sha256`).

Now that we know that, we can then start POSTing commands to run. For a clone, we start with `ls-refs`, which is similar to the first GET we did in the previous protocol, but crucially we can filter the returned values.

This is a little funny, because now in v2 the GET to `/info/refs` does not return refs, it returns capabilities. Then a POST to `/git-upload-pack` with a command is used to actually return the refs we want to inspect (as upload-pack is now just a service endpoint used to run any of several commands).

In this simple example, in practice, there is actually a lot more going over the wire in v2 than in the first version of the protocol. There are 3 round trips consisting of 456 bytes, instead of 2 and 234 bytes.
However, in practical terms, v2 normally saves a lot of traffic because it can filter the references it cares about. Some larger repositories have many megabytes of reference data, so that first refs advertisement is killer overhead.

## What can a Git server do nowadays?

So this is really mostly what I didn't know. What can a git server _do_ these days outside of listing references and negotiating packfiles? What all commands can you tell it to advertise and allow clients to invoke?

The reality is that out of the box, it's pretty much nothing. Outside of `ls-refs` and `fetch` the vanilla server only advertises `server-option` and `object-format`, which aren't actually _commands_, they're just simple ways to pass other data (arbitrary values to custom servers like Gerrit and the hash-format if it's not sha1).

There _are_ other commands, but they're all gated behind server (and sometimes also client-side) config options.

## See it for yourself

You don't need a special setup to watch v2 work. Point <code>GIT_TRACE_PACKET</code> at any modern host and read the conversation:

<Wire
  label="Commands to observe protocol v2 yourself"
  lines={[
    [["cmt", "# Watch the capability advertisement and ls-refs exchange"]],
    ["GIT_TRACE_PACKET=1 git ls-remote https://github.com/git/git"],
    [],
    [["cmt", "# Force a version and compare v0 vs v2 for yourself"]],
    ["git -c protocol.version=2 ls-remote https://github.com/git/git"],
    ["git -c protocol.version=0 ls-remote https://github.com/git/git"],
    [],
    [["cmt", "# Check what your client defaults to"]],
    [
      "git config --get protocol.version   ",
      ["cmt", "# empty ⇒ built-in default of 2"],
    ],
  ]}
/>

Look for the <code>version 2</code> line, the capability list that follows it, and then your client sending <code>command=ls-refs</code>. That's the whole protocol, right there on the wire — the quiet rewrite you've been using all along.
